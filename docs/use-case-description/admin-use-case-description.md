# Use Case Description — ผู้ดูแลระบบ (Admin)

---

## ตารางที่ 1 เข้าสู่ระบบ (Login)

| | |
|:---|:---|
| **Use case name:** | เข้าสู่ระบบ (Login) |
| **Description:** | ผู้ดูแลระบบสามารถเข้าสู่ระบบด้วยอีเมลและรหัสผ่าน เพื่อเข้าใช้งานแดชบอร์ดจัดการระบบ |
| **Primary Actors:** | ผู้ดูแลระบบ (Admin) |
| **Goals:** | ผู้ดูแลระบบเข้าสู่ระบบสำเร็จและเข้าถึงแดชบอร์ดจัดการระบบได้ |
| **Precondition:** | ผู้ดูแลระบบมีบัญชีในระบบ ระบบพร้อมใช้งาน |
| **Postcondition:** | ผู้ดูแลระบบได้รับ JWT Token และเข้าสู่หน้าแดชบอร์ดผู้ดูแลระบบ |
| **Invariants:** | รหัสผ่านต้องตรงกับที่เข้ารหัสไว้ในฐานข้อมูล Token ถูกเก็บใน httpOnly Cookie |
| **Scenarios:** | 1. ผู้ดูแลระบบเปิดหน้าเข้าสู่ระบบสำหรับ Admin |
| | 2. ระบบแสดงแบบฟอร์มเข้าสู่ระบบ |
| | 3. ผู้ดูแลระบบกรอกอีเมลและรหัสผ่าน |
| | 4. ผู้ดูแลระบบกดปุ่ม "เข้าสู่ระบบ" |
| | 5. ระบบตรวจสอบอีเมลและรหัสผ่าน |
| | 6. ระบบสร้าง JWT Token และเก็บใน Cookie |
| | 7. ระบบแสดงหน้าแดชบอร์ดผู้ดูแลระบบ |
| **Alternative:** | **กรณีอีเมลหรือรหัสผ่านไม่ถูกต้อง** |
| | 1. ระบบแสดงข้อความแจ้งเตือนว่าข้อมูลไม่ถูกต้อง |
| | 2. ผู้ดูแลระบบกรอกข้อมูลใหม่ |

## ตารางที่ 2 จัดการประเภทเหตุฉุกเฉิน (Manage Incident Types)

| | |
|:---|:---|
| **Use case name:** | จัดการประเภทเหตุฉุกเฉิน (Manage Incident Types) |
| **Description:** | ผู้ดูแลระบบสามารถเพิ่ม แก้ไข ลบ ประเภทเหตุฉุกเฉิน กำหนดชื่อ ระดับความสำคัญ (Priority Level) และเปิด/ปิดการใช้งาน (Active/Inactive) |
| **Primary Actors:** | ผู้ดูแลระบบ (Admin) |
| **Goals:** | ประเภทเหตุฉุกเฉินในระบบถูกอัปเดตตามที่ต้องการ |
| **Precondition:** | ผู้ดูแลระบบต้องเข้าสู่ระบบสำเร็จแล้ว |
| **Postcondition:** | ข้อมูลประเภทเหตุฉุกเฉินถูกอัปเดตในฐานข้อมูล การเปลี่ยนแปลงส่งผลต่อ dropdown ในหน้าแจ้งเหตุของผู้แจ้งเหตุทันที |
| **Invariants:** | ชื่อประเภทเหตุฉุกเฉินต้องไม่ซ้ำกัน Priority Level ต้องเป็นตัวเลขจำนวนเต็มบวก (1 = สำคัญสุด) ประเภทที่ปิดใช้งานจะไม่แสดงในหน้าแจ้งเหตุ |
| **Scenarios:** | **กรณีเพิ่มประเภทใหม่** |
| | 1. ผู้ดูแลระบบเข้าหน้าจัดการประเภทเหตุฉุกเฉิน |
| | 2. ผู้ดูแลระบบกดปุ่ม "เพิ่มประเภท" |
| | 3. ระบบแสดงแบบฟอร์ม |
| | 4. ผู้ดูแลระบบกรอกชื่อ และระดับความสำคัญ |
| | 5. ผู้ดูแลระบบกดปุ่ม "บันทึก" |
| | 6. ระบบบันทึกลงฐานข้อมูล |
| | 7. ระบบแสดงข้อความ "เพิ่มข้อมูลสำเร็จ" |
| | **กรณีแก้ไขประเภท** |
| | 1. ผู้ดูแลระบบเลือกประเภทที่ต้องการแก้ไข |
| | 2. ระบบแสดงแบบฟอร์มพร้อมข้อมูลเดิม |
| | 3. ผู้ดูแลระบบแก้ไขข้อมูล |
| | 4. ผู้ดูแลระบบกดปุ่ม "บันทึก" |
| | 5. ระบบอัปเดตข้อมูลในฐานข้อมูล |
| | 6. ระบบแสดงข้อความ "แก้ไขข้อมูลสำเร็จ" |
| | **กรณีลบประเภท** |
| | 1. ผู้ดูแลระบบเลือกประเภทที่ต้องการลบ |
| | 2. ระบบแสดงหน้าต่างยืนยันการลบ |
| | 3. ผู้ดูแลระบบกดปุ่ม "ยืนยัน" |
| | 4. ระบบลบข้อมูลออกจากฐานข้อมูล |
| | 5. ระบบแสดงข้อความ "ลบข้อมูลสำเร็จ" |
| **Alternative:** | **กรณีชื่อซ้ำ** |
| | 1. ระบบแสดงข้อความว่าชื่อประเภทนี้มีอยู่แล้ว |
| | 2. ผู้ดูแลระบบเปลี่ยนชื่อและบันทึกใหม่ |
| | **กรณีลบประเภทที่ถูกใช้อยู่** |
| | 1. หากประเภทถูกใช้ในรายการแจ้งเหตุแล้ว |
| | 2. ระบบแสดงข้อความว่าไม่สามารถลบได้ |
| | 3. ผู้ดูแลระบบสามารถปิดการใช้งาน (Inactive) แทนการลบ |

## ตารางที่ 3 จัดการผู้ใช้ — ระงับ/ยกเลิกระงับ (Manage Users — Block/Unblock)

| | |
|:---|:---|
| **Use case name:** | จัดการผู้ใช้ — ระงับ/ยกเลิกระงับ (Manage Users — Block/Unblock) |
| **Description:** | ผู้ดูแลระบบสามารถระงับ (Block) หรือยกเลิกการระงับ (Unblock) บัญชีผู้แจ้งเหตุ (Reporter) หรือพนักงาน (Staff) โดยต้องระบุเหตุผลทุกครั้ง ระบบจะบันทึกประวัติการ Block/Unblock ทุกรายการ |
| **Primary Actors:** | ผู้ดูแลระบบ (Admin) |
| **Goals:** | บัญชีผู้ใช้ที่มีปัญหาถูกระงับ หรือบัญชีที่ถูกระงับก่อนหน้าถูกยกเลิกการระงับ |
| **Precondition:** | ผู้ดูแลระบบต้องเข้าสู่ระบบสำเร็จแล้ว มีบัญชีเป้าหมายในระบบ |
| **Postcondition:** | สถานะ is_blocked ของบัญชีเป้าหมายถูกเปลี่ยน ประวัติการดำเนินการถูกบันทึกในตาราง block_history พร้อมเหตุผลและเวลา |
| **Invariants:** | ต้องระบุเหตุผลทุกครั้งที่ Block หรือ Unblock ผู้ดูแลระบบไม่สามารถ Block ตัวเองหรือ Admin คนอื่นได้ ผู้ใช้ที่ถูก Block ไม่สามารถเข้าสู่ระบบได้ |
| **Scenarios:** | **กรณีระงับบัญชี (Block)** |
| | 1. ผู้ดูแลระบบเข้าหน้าจัดการผู้ใช้ (Reporters หรือ Staffs) |
| | 2. ผู้ดูแลระบบค้นหาผู้ใช้เป้าหมาย |
| | 3. ผู้ดูแลระบบกดปุ่ม "ระงับ" |
| | 4. ระบบแสดงหน้าต่างให้กรอกเหตุผล |
| | 5. ผู้ดูแลระบบกรอกเหตุผลและกดปุ่ม "ยืนยัน" |
| | 6. ระบบเปลี่ยน is_blocked = true |
| | 7. ระบบบันทึกลง block_history (action = BLOCK, reason, admin_id, timestamp) |
| | 8. ระบบแสดงข้อความ "ระงับบัญชีสำเร็จ" |
| | **กรณียกเลิกการระงับ (Unblock)** |
| | 1. ผู้ดูแลระบบเข้าหน้าจัดการผู้ใช้ |
| | 2. ผู้ดูแลระบบค้นหาผู้ใช้ที่ถูกระงับ |
| | 3. ผู้ดูแลระบบกดปุ่ม "ยกเลิกระงับ" |
| | 4. ระบบแสดงหน้าต่างให้กรอกเหตุผล |
| | 5. ผู้ดูแลระบบกรอกเหตุผลและกดปุ่ม "ยืนยัน" |
| | 6. ระบบเปลี่ยน is_blocked = false |
| | 7. ระบบบันทึกลง block_history (action = UNBLOCK, reason, admin_id, timestamp) |
| | 8. ระบบแสดงข้อความ "ยกเลิกระงับสำเร็จ" |
| **Alternative:** | **กรณีไม่กรอกเหตุผล** |
| | 1. ระบบแสดงข้อความว่าต้องกรอกเหตุผล |
| | 2. ผู้ดูแลระบบกรอกเหตุผลและยืนยันใหม่ |

## ตารางที่ 4 ตรวจสอบรายงานปัญหา (Review User Reports)

| | |
|:---|:---|
| **Use case name:** | ตรวจสอบรายงานปัญหา (Review User Reports) |
| **Description:** | ผู้ดูแลระบบสามารถดูรายการรายงานพฤติกรรมที่ไม่เหมาะสมที่ส่งเข้ามาจากผู้แจ้งเหตุหรือพนักงาน ตรวจสอบรายละเอียด และอัปเดตสถานะ (REVIEWED / DISMISSED) พร้อมเขียนบันทึกการตรวจสอบ |
| **Primary Actors:** | ผู้ดูแลระบบ (Admin) |
| **Goals:** | รายงานทุกรายการถูกตรวจสอบและดำเนินการอย่างเหมาะสม |
| **Precondition:** | ผู้ดูแลระบบต้องเข้าสู่ระบบสำเร็จแล้ว มีรายงานที่สถานะ PENDING |
| **Postcondition:** | สถานะรายงานถูกเปลี่ยนเป็น REVIEWED หรือ DISMISSED พร้อมบันทึก reviewer_notes, reviewed_at และ reviewed_by |
| **Invariants:** | รายงานที่ตรวจสอบแล้วไม่สามารถเปลี่ยนกลับเป็น PENDING ได้ |
| **Scenarios:** | 1. ผู้ดูแลระบบเข้าหน้ารายงานปัญหา |
| | 2. ระบบแสดงรายการรายงานทั้งหมด |
| | 3. ผู้ดูแลระบบเลือกรายงานที่ต้องการตรวจสอบ |
| | 4. ระบบแสดงรายละเอียด (ผู้รายงาน, ผู้ถูกรายงาน, สาเหตุ, เหตุการณ์ที่เกี่ยวข้อง) |
| | 5. ผู้ดูแลระบบตรวจสอบข้อมูล |
| | 6. ผู้ดูแลระบบเลือกสถานะ (REVIEWED หรือ DISMISSED) |
| | 7. ผู้ดูแลระบบเขียนบันทึกการตรวจสอบ |
| | 8. ผู้ดูแลระบบกดปุ่ม "บันทึก" |
| | 9. ระบบอัปเดตสถานะรายงาน |
| **Alternative:** | **กรณีต้องการ Block ผู้ใช้เพิ่มเติม** (extend: จัดการผู้ใช้ Block/Unblock) |
| | 1. ผู้ดูแลระบบตรวจสอบรายงานแล้วเห็นว่าควร Block ผู้ถูกรายงาน |
| | 2. ผู้ดูแลระบบเลือกสถานะ REVIEWED |
| | 3. ผู้ดูแลระบบไปหน้าจัดการผู้ใช้เพื่อดำเนินการ Block |
